## Where the spec was checked against the real data ([verify] items) and differs
| Spec | Reality / what I did |
|---|---|
| Hourly steps, usual for that hour (4.1, 5) | **Not in the store**: `step_count` is one date-only row per day. Steps are a daily measure (compared with the baseline profile, available at end of day). |
| Blood pressure judged against the profile (4.2a) | The baseline has **no BP profile** (BP is not a baseline stream). The usual is computed from earlier BP readings (median, population SD, needs 14 earlier readings), same definition as the profile. |
| Severe statuses `critical_high` / `critical_low` | The evaluator never emits them (statuses seen: normal, borderline_low/high, low, high). The severe path fires only on position `far`. |
| Profile example keys `stream`, `as_of` | `get_profile_asof` returns `n_days, median, sd, flat_band, usual_status, status_days, share_non_normal` only. Not needed by the engine. |
| "Use the Baseline Engine's own cleaning" (R2) | Only glucose has a cleaning rule in the baseline (device range + jump). It is applied to glucose; other streams are accepted as stored. |
| Heart rate for the usual | The full 15-minute stream is in `context_events`; `raw_events` holds only zero-step readings. The engine reads `context_events` and takes the clinical status from `raw_events` when that timestamp exists there (otherwise null, as in the spec example). |

## Assumptions where the spec is silent or ambiguous
1. **Time of an item:** `opened_at`, `peak_at`, `closed_at` and the hand-off's `written_at` are the moment the triggering value became available (as in the spec's ids `sleep_duration_...T07:00`, `..T07:08`), not the 15-minute tick that noticed it. The snapshot's `as_of` is the tick.
2. **`value_time` of a date-only record** is the moment it becomes available (21:00 for medicines, midnight for end-of-day records). The spec's hba1c example counts age from the lab date's midnight; mine counts from the end of that date. It is not current either way.
3. **Diary:** an entry with its own timestamp is available from it (3.1); the configured `21:00` is used only for untimed entries.
4. **Opposite direction:** while an item is open, a reading in the other direction counts toward closing it (the item's direction is fixed); the new run can open a new item at once.
5. **Stale versus overdue (changed after review):** a *continuous* value past its freshness limit is stale: its run is cleared and its open item closes (`close_reason: stale`). A *daily, periodic, count or lab* measure is *overdue* when its age exceeds cadence x `overdue_grace` (config, 1.5; cadence from `cadence: daily` / `cadence_days` / `cadence_minutes`): until then the last value stands, `current` is informational, and an open item stays open until a newer value arrives (R10) or the measure becomes overdue (`close_reason: expired`, closed at the moment it became overdue). Medicine items therefore stay open past midnight. Labels (mood) are informational only.
6. **R1:** only the newest available value per measure is taken at a tick (with a 15-minute tick and cadence this is every reading for glucose and heart rate).
7. **Profile-based usuals** need 14 earlier days/readings (the early-days rule), not `min_samples_usual` (30), which applies to reading-level usuals. A reading-level usual below 30 samples is null (`no_usual:<key>` quality code, my addition).
8. **The usual for a value never contains the value (changed after review):** an end-of-day value (hydration, screen time, sedentary time, steps) becomes known at the next midnight but belongs to the day before; it is judged against the profile as of the START of its own date (`Obs.record_date`), which excludes it. A test recomputes the usual independently for every daily value and checks that the value's own date is never inside. Effect on the real run: 4 items changed (3 closed one to three days later, 1 peaked higher), 1 item disappeared and 2 appeared, all on end-of-day measures; no other measure changed.
9. **Persistence labels:** a reading below `open_label` resets the run; a reading between the two labels (possible only if configured with a gap) neither opens nor closes.
10. **`state_items` extras:** `close_reason` and `peak_metric` columns; the State Engine writes its own database file (`output/state_engine.db`), tables `state_log`, `state_items`, `state_handoffs`. Nothing is written to the store or `memory_v2`.
11. **`any_stale`** counts only stale continuous measures and overdue daily or periodic measures (it was 91.0% of ticks when every measure used the freshness limit; it is 18.8% now).
12. **`yesterday_memory_headline`** is the baseline's gist headline or code line for yesterday's day window (it can be a code line).
13. **Meal kind** is a label-text match in the configured order (`snack_lunch` counts as lunch, `late_dinner` as dinner), as the spec says.
14. **`usual_alt`** is computed for glucose only (the only measure with two bases).
15. **Adverse and favourable items (added after review):** each measure that can open an item names its `adverse_directions` in config (glucose, heart rate, resting heart rate, blood pressure, screen time, sedentary time: `above`; sleep, steps, medicines, hydration: `below`; a stream without them is refused). An item whose direction is not adverse gets `item_class: favourable`: it is recorded (`state_items`, snapshot `open_item_class` / `open_item_classes`, `state_log`) and opens and closes by the same rules (`n_open`, `n_close`, labels, usual, freshness unchanged) but **no hand-off is written**, unless at opening the carried clinical status is abnormal (low / high, not borderline) on that side or the position is `far`; then it is `adverse`. The class is fixed at opening. **For a `kind: continuous` measure the carried clinical status is not used for that exception, only a `far` position is** (continuous heart rate's status comes from judging sleeping readings against an awake resting range). Real run: 565 items (identical throughout), 287 adverse, 278 favourable; hand-offs 565 -> 316 -> 287 (`docs/state_engine_handoff_change.md`, `docs/state_engine_final_counts.md`).
