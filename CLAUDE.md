# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

UMC (Unified Medical Context) upstream layer: a deterministic, lookup-only pipeline that runs one patient's year of readings (Oct 2025 – Sep 2026, patient `meera_iyer_v1`) through a **Signal Plausibility Filter**, a **Threshold Evaluator**, a **Short-Range Event Linker**, a **Personal Data Store**, and a **Baseline Engine**. No ML/LLM anywhere in the first two components; the `reason` field must stay a templated string built from the values checked. The full spec for those two is `task/components.md`; the list of files to evaluate is `task/inputs.md`. Components 3–5 are not in `task/` — they were specified directly in conversation; see below. The Baseline Engine is the pipeline's first and only node that calls an external API (an LLM) — everything upstream of it is pure deterministic Python.

## Commands

Python 3.12, managed with `uv`. Tests: `uv run python -m pytest -q tests` (one test per configured anchor plus the stream-table logic). No lint config.

```bash
uv sync                # install
uv run v0-code         # run the graph: writes the 3 result CSVs + output/personal_data_store.db, prints a verification report
uv run v0-code --glucose-caption   # also run the legacy per-window glucose caption LLM (off by default, ~5 min)
uv run v0-plot         # one PNG per biomarker in output/plots/ (needs v0-code run first)
```

Both commands take `--data-dir final --ranges-dir ranges --output-dir output` (these are the defaults, relative to the repo root).

Doctor-facing dashboard (separate `dashboard/` folder, no build step, ECharts vendored in `dashboard/vendor/`):

```bash
uv run python dashboard/build_data.py   # CSV/JSON -> dashboard/data/*.json (runs the pipeline first if output/ is missing)
uv run python dashboard/serve.py        # http://127.0.0.1:8765 (add --rebuild to regenerate data, --no-open to skip the browser)
```

## Architecture

LangGraph pipeline (`graph/builder.py`): `load_inputs → plausibility_filter → (conditional) → threshold_evaluator → short_range_linker → personal_data_store → baseline_engine`. The conditional edge ends the run early if no reading passed the filter.

- `graph/state.py` holds the single Pydantic `UMCState` plus the `Reading` / `FilterResult` / `ThresholdResult` / `Pairing` records. Nodes return partial dict updates that merge into it.
- `nodes/` are thin wrappers: read state, call pure logic, write the CSV, return updates. Decision logic lives in `logic/plausibility.py`, `logic/threshold.py` and `logic/linker.py` with no LangGraph imports, so it stays unit-testable and new (e.g. LLM) nodes can be added without touching it.
- `data/loaders.py` normalizes every source file into `Reading(event_id, biomarker, timestamp, value)`. `WIDE_FILES` / `LONG_FILES` there are the mapping from file columns to biomarker names. It also has separate, non-`Reading` loaders for the linker's raw context data (meals, adherence, context events, sleep, mood, diary) — these keep fields `Reading` doesn't have (food description, medication name, mood label, etc.).
- `viz/plots.py` reads the two output CSVs (not the graph) and draws threshold bands from `ranges/threshold_ranges_full.csv`.

Output row order is just loader order (not sorted).

Dashboard (`dashboard/`): `build_data.py` is the only Python; it reads `final/`, `output/` and `output_for_doctor/` and writes compact JSON with presentation-only aggregation (no new analysis). Timestamps are encoded as IST wall-clock-as-UTC epoch ms so ECharts (`useUTC`) shows IST; `output_for_doctor` event windows are UTC and are converted. The front end is vanilla ES modules: `js/app.js` (hash router) → `js/views/*.js` (each exports `render(root, args)` returning breadcrumbs), shared chart code in `js/charts.js` (`glucoseLayers` is reused by month/week/event/episode views), data indexes in `js/store.js`. Event `date` in `output_for_doctor` is the UTC date, so `ist_date` (from the window) is used for placement and `date` for the same-day context.

## Non-obvious decisions (check before changing)

- Input files: the four split lab files are used instead of `lab_panels_yearly.csv`, except `fasting_glucose`, which exists only there. `tsh`, `hsi` and the excluded files in `task/inputs.md` are not evaluated.
- Name mapping: data `cgm_glucose_reading` is judged against the `fasting_glucose` threshold row (there is no CGM row). `hdl_c`, `creatinine`, `waist_hip_ratio` resolve to `_male`/`_female` rows from `final/sex_fact.csv`; `ggt` has sex in its `age_group` column. Age comes from the DOB in `final/age_fact.csv` at each reading's date.
- `continuous_heart_rate_yearly.csv` (15-min wearable stream, biomarker `continuous_heart_rate`) reuses the `resting_heart_rate` rows: bounds in the filter, and the 60–100 range in the evaluator. Because that range is for *resting* HR, the evaluator only judges readings in an hour with `steps == 0`; readings during activity or with no step row are counted in `state.not_applicable` and get no status (see `logic/threshold.py:skip_reason`). The reference CSVs have no continuous-HR row and are intentionally unmodified.
- `steps_hourly` is plausibility-checked hourly, then summed to a daily `step_count` for thresholds.
- `event_id` is NOT unique in the source files (glucose, steps, sleep, vitals, weight and lab ids restart each month: 2,976 unique ids over 33,581 glucose rows). Never join or filter readings by `event_id` alone — pair by position or by `(event_id, timestamp)`.
- Blood pressure `"129/86"` is split into systolic and diastolic readings.
- Context check (glucose/BP/HR only): steps are matched by hour bucket (`timestamp[:13]`), location by date (location data is daily). "Active" means steps > 0 or a location other than `home`/`home_wfh`; context present but not confirming gives `FLAGGED_ERROR`. All other out-of-bounds values are `CONFIRMED_ERROR` with no context check.
- Status assignment (`logic/threshold.py:assign_status`) is side-based because the CSV's `abnormal_high` column holds the abnormal cut-point even for low-side rows (e.g. egfr, HDL). No critical tiers exist in the table, so `critical_*` is never emitted.
- `confidence_source` is intentionally blank: the threshold CSV has no such column, and values must not be invented.
- Weight has no threshold row, so it is filtered but not evaluated.

## Component 3: Short-Range Event Linker (`logic/linker.py`, `nodes/short_range_linker.py`)

Scope: **glucose only** — only `cgm_glucose_reading` rows from `threshold_results` with `status in {high, low}` are considered (borderline and `fasting_glucose` are excluded, per instruction). For each qualifying reading, checks 8 candidate types for temporal proximity and emits one `Pairing` row per match found — never a causal claim, just "this happened nearby." Output: `output/short_range_pairings.csv`.

Per-type matching policy (confirmed in conversation, not all from a written spec — revisit if requirements change):
- **meal** (≤150 min before), **activity** (hourly step bucket starting ≤90 min before, steps > 0), **context_event** (same calendar date): emit one pairing *per matching item* — these are genuinely separate occurrences, so a reading can get several.
- **medication**: one pairing per medication logged that calendar date; `candidate_timestamp`/`lag_minutes` are always null — adherence has no timestamp, and time was explicitly excluded from this check.
- **heart_rate**: one *summary* pairing (avg/min/max/n) over `continuous_heart_rate` readings within ±120 min — the stream is dense (15-min cadence), so one row per raw sample would just be redundant oversampling of the same signal.
- **sleep**, **mood**, **diary**: at most one pairing (one sleep row per night already date-aligned to the wake day, one mood row per time-block, one diary entry per day).
- **mood time-block**: a glucose reading's hour is mapped to morning (05–11), afternoon (12–19), evening (20–04) — this mirrors the diary's own stated 3-block scheme (diary's "afternoon/evening" + "night" are merged into "evening" to match the mood file's 3 labels), not a thirds-of-the-day split.
- Candidate ids (`adherence_id`, sleep `event_id`, etc.) are **not unique across the year either** — same caveat as glucose `event_id` above. Always key a pairing by `(glucose_event_id, glucose_timestamp)`, not `glucose_event_id` alone (the node does this for its own summary counts — see the comment in `short_range_linker.py`).

## Component 4: Personal Data Store (`data/store.py`, `nodes/personal_data_store.py`)

Pure write-in/read-out SQLite layer (`output/personal_data_store.db`, one table `raw_events`) — no computation. Holds every Threshold Evaluator output row (all 44,469, every status including `normal`) and every Short-Range Linker pairing (138,118); nothing else reaches it.

The spec's literal schema (`event_id TEXT PRIMARY KEY`) can't work: `event_id` repeats across the year, and one glucose reading can have several pairings sharing the same `event_id`. Fixed (confirmed in conversation) by giving `raw_events` a surrogate `id INTEGER PRIMARY KEY AUTOINCREMENT` and keeping `event_id` as an ordinary column; `get_pairings` takes `(glucose_event_id, timestamp)`, not `event_id` alone; `insert_pairing` takes the pairing's `timestamp`/`biomarker`/`value`/`status` too, so a pairing row is self-contained (no join needed to know what glucose reading it's about).

`PersonalDataStore(path, reset=True)` is only ever passed by the pipeline node (rebuilds the table fresh each run, like the CSVs). A plain `PersonalDataStore(path)` (the default, `reset=False`) opens the existing store without touching it — this exists because the obvious bug (constructor always dropping the table) wiped the DB the first time it was opened just to read it; don't reintroduce an unconditional drop in `__init__`.

## Component 5: Baseline Engine — cross-domain memory (spec: `task/baseline.md`) — IN REVIEW, not wired

Principle: `record_json` (code-computed, complete) is the detail; `memory_json` (LLM) is a *curated interpretation* on top of it, never a field-by-field restatement. Code computes every number, direction, delta, co-movement pairing, anchor crossing and data-quality flag; the LLM only describes them.

**Built and running every pipeline run (numeric only):** `nodes/baseline_engine.py` ingests non-threshold streams into `context_events` (`data/context_ingest.py`, serialized from what `load_inputs` already parsed — no second CSV read), then `logic/memory_records.py` builds 710 records (352 day, 346 rolling-week, 12 checkpoint-month) into `memory_records` with `llm_status='skipped'`. Streams/expected cadence live in `logic/registry.py`; anchor thresholds in `logic/anchors.py` (per-tier, user-tuned: day drops GMI, adherence = count of medications changed vs `min(2, n_meds)`, steps are absolute floors). `numeric_summary` is still written with all numeric columns; its legacy per-window LLM caption (`judge_windows`, nano, ~5 min) is OFF by default and only runs with `--glucose-caption` (`state.glucose_caption_llm`). A pipeline run rebuilds the whole DB (`reset=True`), so captions from an earlier `--glucose-caption` run are not preserved across runs.

**Record conventions worth knowing:**
- `anchors_crossed` is decided by code. `anchors_questionable` = crossed severe-range anchors whose window (or its prior window — a "cleared" crossing is the prior artifact leaving) carries `max_reading_above_400`, `known_clip_artifact_reading` or `implausible_rate_of_change`. The LLM may set `is_notable=false` only when every crossed anchor is questionable; empty `anchors_crossed` forces false; otherwise it must be true. `has_diary_event` (the 129-entry context log) never makes a window notable.
- `co_movement_candidates` (day from deltas, week from `stream_direction_table`; absent at month tier) lists streams that moved the same/opposite way as glucose; directions use `FLAT_BANDS` (config). Month `deltas` compare trailing-30-day means with the *previous checkpoint*; `domain_trends` (first vs latest month, with signed delta) and `lab_link.gap_hba1c_minus_gmi` are code-computed so the LLM never infers a difference.
- Generic `low_completeness:<stream>:<pct>` flags (<70%); 12 days have no step data (the hourly steps file covers 340 days). A missing step hour is *unknown*, not zero steps — treating it as rest once made `resting_period_mean` equal the all-day mean on those days. `resting_period_mean` (mean of 15-min readings at rest) is what the resting-HR anchor/deltas use; `resting_heart_rate_daily` is a different single daily value — never mix them.
- `material_changes` (day/week/month records) is built in code and is what `render_material` must show: anchors crossed (on cleaned values), missed doses, **statuses that are non-normal AND differ from the stream's usual** (`MemoryData.usual_status`: the most common day-level status over the whole dataset, defined from 14 days — so steps "low" on 95% of days is not news), diary events, data gaps / low completeness, and every removed questionable reading (`questionable_reading` items with time and value). `quiet` = empty (never true at month tier). **Quiet counts: 26 of 352 days (7.4%), 0 of 346 weeks.** Glucose's own per-reading status is excluded (fasting cut-offs). `tests/test_rendering.py` has one invariant test per kind on the real pipeline output plus golden windows (week ending 2025-11-22 shows sleep down, adherence down, resting HR up, glucose up; week ending 2025-12-09 is not notable).
- Week `best_day`/`worst_day`: TIR ties break by mean glucose (best = lowest mean, worst = highest); if all 7 days are identical both are null and `best_and_worst_day_note` says so. Daily `worst_mood_category` ranks by distress (`DISTRESS_RANK`), so `positive_uplifted` is never "worst" while anything else was recorded. A day's mood value counts only strain blocks (`logic/patient_config.STRAIN_CATEGORIES`: mild stress, tired, anxious, overwhelmed); calm and uplifted do not count.
- Questionable readings (`logic/data_quality.py`): clipped 65.0, >400, or an implausible jump's endpoint. Windows holding any carry `questionable_excluded` (metrics recomputed without them, raw beside them) on glucose sections, post-meal peaks/aggregates and `deltas` (cleaned changes need no questionable reading in EITHER window). Each flag has an `affects` list (`FLAG_AFFECTS`; e.g. the clipped 65.0 affects only `tbr_pct`, `tbr_severe_pct`, `min_value`) stored as `data_quality_details`. **Anchors are evaluated on the cleaned changes** (`effective_deltas`): `anchors_crossed_raw` is what they would have said on raw values and `anchors_suppressed` the difference (crossings that existed only because of a bad reading). Effect: `severe_range_appeared_or_cleared` now never fires (all 4 day / 28 week / 4 month raw crossings were artifacts); notable rates day 31.8%, week 30.1%, month 33.3%.
- `stream_change_table` (value minus the previous window's value, per numeric stream) and `co_movement_candidates.ranked` (same/opposite co-movers with direction, unsigned amount, unit, strongest first by |change| / flat band). The entry must cover the top K (4; 2 on a quiet window), one measure per item.
- Month anchor `lab_cgm_discordance` (config 0.5, **inclusive**, month only): fires when |lab HbA1c − GMI over the 90 days before the lab| ≥ 0.5 for a lab drawn inside the checkpoint's own 30 days (`deltas.lab_cgm_gap`). Fired 3 of 12 checkpoints.
- Deliberate non-bug: Threshold Evaluator glucose `status` (70/99/125, diagnostic) vs CGM metrics (70/180/250/54, management) disagree by design.

**Memory entries v2 — code renders every fact, the model writes only the interpretation (`nodes/memory_writer.py` + `logic/render.py`) — current design, sample-tested, NOT wired into the node; `memory_json` is never persisted yet.** `render_window(record)` writes, in code, the material changes (every missed dose, diary entry verbatim with its date, status unusual for the stream, data gap, removed questionable reading, anchor crossing with its numbers), the numbers (questionable readings removed), what changed vs the previous window, the top co-movers (direction + amount, mood worded "N fewer/more strained periods of the day"), the trajectory (by time of day / day by day / month by month), caveats and the steady streams. The model reads that text and returns only `headline`, 3–5 `what_stood_out` sentences and a `notable_reason`; `is_notable` is forced by code (anchors crossed on cleaned values and not all questionable). Checks kept: numbers grounded in the rendered text (10% tolerance), no causal language, direction agrees with the code tables (single-measure sentences only), notable rule, no dates, no quotes / copied diary text. Setting words ("supervised", "clinic") are a prompt rule only. The older validators below are kept and run only with `memory_writer.STRICT_VALIDATORS = True` (default off). A window failing twice is stored code-rendered with `llm_status='rejected'` — the numeric record and every rendered fact survive any LLM failure. Batch sizes day 8 / week 4 / month 2 (a window's text is ~0.6–0.9k tokens).

**Legacy flow (`nodes/memory_llm.py`, the model wrote statements with evidence refs) — superseded, kept for the strict flag and its tests.** Batches: 4 windows/call (day), 2 (week), 1 (month) = 273 batch calls for the full run, plus one single-window retry per failing window.

Four layers keep the model inside the lines, in this order:
1. **Annotate + plain copy (`logic/record_view.py`).** `annotate` prepares the record for the model *and* the validator (so what it was shown and what it is checked against never drift): affected metrics take their cleaned value with a `<metric>__note` beside them, raw flagged values live only in a `questionable_readings` section (for `data_quality_caveats` only), the code-side direction/change/candidate tables are replaced by `stream_movement` and `co_movement_required`, and the model never sees the word "anchor" (`large changes found`). `to_plain` then renames keys to plain English with units, turns category/status values into words (`calm_stable`→calm, `borderline_low`→slightly below the reference range, medicine ids → names, directions → "went down"), and returns a plain-path → internal-path map so `evidence_refs` resolve back in code (`Refs`: also accepts internal paths, sloppy casing, a `record.`/`prior.` prefix, and a dropped leading section when exactly one real path ends with it). A label must never contain a system word ("whole record so far" put "record" in the model's mouth).
2. **Sanitizer.** Leaked internal key names, category values, data-quality flag names (→ plain phrases) and short dates ("12-24") are rewritten in code before validation; every substitution is logged to `SANITIZED`. Approximations are fine (V0), but causal language and ungrounded numbers are deliberately *not* sanitized — they fail and retry.
3. **Validation.** Schema + per-window caps; numeric grounding **with tolerance** (V0: within 10% of a record value, or within 1 unit when the value is under 10; a range is grounded when a record value falls inside it; band edges 54/70/180/250 shown in labels are allowed; `GROUNDING["tolerance_only"]` counts how often the tolerance did the work — 0–3 per ~200); forbidden-stem scan; system-voice scan (anchor, crossed, stream, "the record", field, direction table, `direction:`-style fragments; the plain word "note" is fine); **wrong direction is a rejection**; a questionable-reading caveat may not be put on a metric no flag affects (hard when only unaffected metrics are cited, soft when an affected one is cited too); a flagged raw value outside `data_quality_caveats` is rejected; flag names outside caveats are rejected; co-movement = exactly the top-K code-chosen measures, one per item, each stating direction (up/down) and the amount; a missed dose must be named; notability rule. Soft (counted, not rejected): "steps was low"-style status echoes, a change citing a noted metric without the caveat, diary events not quoted. Refs into the `things that deviated` checklist are dropped, not failed (`IGNORED_REFS`).
4. **Code-computed fields.** `unremarkable_streams` (flat, no anchor, not cited) and `confidence` are filled by code after validation; the model does not write them.

`caps_for(record)` shortens the entry for a quiet window (`record["quiet"]`, i.e. empty `material_changes`): headline + 2 key observations, no trajectory/changes/patterns, at most 2 co-moving measures. A window the code says deviated gets the full caps — and, as sampled, fills them (day 2025-12-26: 22 statements). One retry with the specific failures appended; then `llm_status='rejected'` (numeric record untouched).

Lessons: always save raw responses to a uniquely named file per run (a shared `/tmp` file was once overwritten by a stray process); replay saved responses through the validator offline instead of iterating on live calls; and when a sample looks wrong in a way the code should have fixed, check whether `record_json` predates the change — records are rebuilt only by a pipeline run.

**Registry-driven tables (`logic/registry.py` rows + `logic/stream_tables.py`, no per-stream branches):** each `Stream` carries `label` (plain name), `path` into the day record, `agg` (mean | sum_mean | counts | list | adherence | mood | meals | crossings) and `numeric`. From that: week `aggregates` (mean of daily values; steps sum + per-day mean; adherence overall % + taken/expected per medicine; mood counts per category per time block; meals by label + mean/max post-meal peak, foods only for best/worst day; location day counts; per-stream completeness), `stream_direction_table` for every numeric stream (flat band = 0.5 × SD of the stream's earlier daily values, `FLAT_BAND_OVERRIDES` to override; too little history or <4 days in either window → `insufficient_data`), and `deltas_vs_cumulative` (window value − mean of daily values *before* the window; null while unreliable). Mood is the count of non-`calm_stable` blocks. `co_movement_candidates` is built from the direction table (day and week). `confidence` is computed in code (high = reliable and glucose completeness ≥90%; moderate = reliable and ≥70%; else low) and copied onto the entry — the model does not write it.

**Safeguards:** `tests/test_anchors.py` has a trigger-fires/quiet-silent test for every anchor in `ANCHOR_NAMES`; `tests/test_memory_llm.py` covers the annotated view, resolver, sanitizer, tolerance, direction, voice, caveat scoping, raw-value leakage, co-movement and missed-dose checks; `tests/test_records_logic.py` covers best/worst ties, mood rank, material changes, questionable readings, cleaned changes and co-movement ranking. The run report lists per-anchor fire rates per tier and any "dead" anchor (configured, never fired): week `glucose_TIR_change_points` and month `glucose_TIR_change_points` / `glucose_CV_change_points` / `sleep_hours_change` have never fired on this dataset, and `severe_range_appeared_or_cleared` is now dead in every tier once artifacts are removed (`lab_cgm_discordance` fires 3/12). Dead anchors are reported, never silently retuned.

**Co-movement naming:** `MERGE_DOMAINS` in `logic/stream_tables.py` folds a domain's near-duplicate streams into one name, so co-movement says "heart rate" once instead of listing heart rate, resting heart rate and daily resting heart rate. Only `heart_rate` is merged; `lifestyle` deliberately is not (hydration, screen time and sedentary time are different things).

**Not built yet:** §13 final report; other biomarkers' clinical metric sets; persisting `memory_json` / wiring `memory_llm` into the node (awaiting approval of the sample).

## Baseline Engine v2 (spec: `task/baselineV2.md`) — Stages A–D built and run (day, week, month tiers; gists written for all 590 windows that need one)

A rebuild of the Baseline Engine's structure. **Code computes every fact; the LLM (Stage C/D, not built) will write words only.** Lives in `src/v0_code/baseline_v2/`, reads only the store (`raw_events`, `context_events`) plus one YAML config (`config/patient_meera_iyer_v1.yaml`), writes only the new `memory_v2` table. The v1 tables, `nodes/memory_writer.py` and `nodes/memory_llm.py` are untouched and still work.

```bash
uv run python -m v0_code.baseline_v2.run --stage A              # day tier -> memory_v2 (upsert; NEVER wipes) + output/baseline_v2_stage_a_*.md
uv run python -m v0_code.baseline_v2.run --stage B              # all three tiers (day rows are rebuilt identically) + output/baseline_v2_stage_b_*.md
uv run python -m v0_code.baseline_v2.run --stage A --rebuild    # drops and recreates memory_v2 only
```
`uv run v0-code` now refuses to run if `output/personal_data_store.db` exists unless `--rebuild` is passed (a rebuild wipes the v1 memory entries).

Modules: `config` (YAML -> `Config`, versioned by content hash; thresholds like `min(2, n_meds)`), `data` (`StoreView`: store grouped by local day in the config timezone), `trust` (clean first: device range + jump rule scaled by the gap; ADA metrics reused from `logic/baseline_glucose._metrics`; reliability; the "with them included" twin), `profile` (median/SD/flat band/usual status from history strictly before the window), `tags` (direction + size label vs her own flat band; co-movement, one entry per domain, only when glucose moved), `anchors` (config-driven, evaluated on cleaned values; a crossing that exists only on raw values goes to `anchors_questionable`), `material` (typed list; `quiet` = empty), `render` (`deviation_text` and code lines, all by code), `engine` (`build_days`), `storage` (`MemoryV2Store`: upsert + `get_memory / get_memories_between / get_notable / get_profile_asof`, parsed objects, `facts` only with `full=True`), `report`, `run`.

Things worth knowing before changing it:
- Nothing patient-specific in code: timezone, pronoun, medication-id convention, strain categories, device range, jump limit, anchors, streams (one YAML row each; `agg` picks a generic aggregator). `tests/test_v2_fixture_patient.py` runs a second synthetic patient (UTC+0, 2 medicines, no mood or heart rate, other step floor) through the engine with config only.
- As-of everywhere: the profile for day D uses days < D; `tests/test_v2_invariants.py` rebuilds from a truncated store and from a store with the removed readings deleted to prove no look-ahead and that a questionable reading moves nothing.
- Gist status is NULL until the LLM stage runs, except `code_line_early` (< 14 days of history) and `code_line_quiet`. An upsert keeps a gist written by the LLM (`gist_ok` / `gist_retry_ok`) but does not yet detect that its facts changed (parked).
- Day-level threshold status = the most common status among the day's readings; "worse than usual" = higher severity rank than the stream's usual status, AND at least `min_material_status` (config, default `abnormal` = low/high only; `borderline` also counts borderline_*). Borderline statuses are always shown next to the value in the numbers. BP is listed in facts only (no deviation logic). The v1 hourly-steps-based "resting period" heart rate is not rebuilt (needs steps by hour, which is not in the store): `resting_hr_change_bpm` uses the daily resting value.
- `adherence_meds_changed` counts only medicines that went taken -> missed (`engine.meds_worsened`); a recovery still shows in "what changed". A measure already reported by another material item (a crossed anchor, a missed dose, a status deviation) gets no second "large move" line. A count of periods (mood) is always "strained periods of the day: N more / N fewer" (`direction_word` on tags, co-movement entries and large-move items), never "mood up/down".
- Measured on this patient (Stage A after review round 1): quiet 79/352 (22.4%) at `abnormal`, 42/352 (11.9%) at `borderline`; notable 67/352 (19.0%) under both. Anchors dead on the day tier: `severe_range_appeared_or_cleared` (its only 4 crossings were artifacts).
- Stage B (`windows.py`): week = rolling 7 days for every day from the 7th (346), compared with the 7 days before; month = cumulative from day 1 plus the last 30 days, a checkpoint every 30 days and a final partial one (12), compared with the previous checkpoint's last-30 window. A window value is the mean of the daily values (needs `min_days_in_window` days), glucose pooled over the cleaned readings, adherence taken/expected; flat bands come from daily values strictly before the window starts. Week and month material changes are aggregated from the day windows' own items (missed doses as "N of 7 days", statuses worse than usual as "on N of 7 days"). Week gist status: `code_line_early` (< 14 days of history or no previous window), `code_line_quiet`, else pending for the LLM. `gist.week_gist_weekday: none` (current) means every such week is queued; a weekday name would queue only that weekday's weeks plus any with an anchor crossed and give the rest `code_line_week_skipped`. Month: `chronic_findings` (streams non-normal on >= `chronic.min_share_pct` of days so far, recorded once here) and `lab_link` (each lab next to the GMI over the prior 90 days, signed gap; the anchor looks only at labs drawn in the checkpoint's last 30 days, threshold inclusive). Mood ranking for a day's "worst mood" comes from config `mood_distress_order`.

Things worth knowing: weeks are Monday to Sunday in the patient's zone, ISO names; an entry belongs to the week of its `as_of` (not its `local_date`); the weekly job runs for every week end strictly before the next event, the first week is the week of the first day of the data, the last job runs at the last day 23:59:59 (partial week). Week label from the Evidence store's daily labels by date (`support` and `flags` only; a day with no record is `insufficient`; a partial week counts only the days that exist, threshold `ceil(5/7 x days)`; fewer than 4 days is `insufficient`). The lifecycle (`lifecycle.py`) is a pure function of the weekly labels: a count is a run of equal decisive labels reset by the opposite decisive label (amendment 35), so back-fill on creation equals stepping week by week; a new version of a long-term memory is written only when it is created or its status, counters, flags, finding ids or text change. Counters count dates (each date keeps the case ids that made it, so a date counts once and a current case can be excluded from `seen_before`). `evidence_refs`: the last day with a record in each decisive week. Result on this patient: 51 weeks (2025-W40 to 2026-W38), 284 entries, 29 long-term memories (174 versions): 25 supported, 3 candidate, 1 retracted at the end; 26 reach supported (15 of the 29 were created as supported by back-fill), one is weakened (2026-W22) then retracted (W28); no memory has the `contrary` flag. Determinism, idempotency and the independent as-of audit (`audit.py`: 4,948 weekly labels and 34,246 evidence days re-read, none after its job) all pass.

## The loop, stage L1 (Findings reads PI as-of; code layer only; report `docs/loop_l1_report.md`) — built, tested, run; L2 (the model texts in the loop) NOT started

No model, and no stream, measure, medicine or patient name in the code (a test enforces it).

```bash
uv run python -m v0_code.loop_engine.run --config config/loop_meera_iyer_v1.yaml              # Findings LIVE in time order with PI -> output/findings_loop.db + output/pi_loop.db, then the three as-of audits (about 3 s)
uv run python -m v0_code.loop_engine.run --config ... --max-events 150                        # stop early; running again continues (resumable, idempotent)
uv run python -m v0_code.loop_engine.run --config ... --rebuild                               # drop and recreate the loop's own tables (explicit)
```
How it works: `findings_engine.loop.replay` is the clock; optional `hooks` run PI's weekly jobs before each event whose time is past a week end and `record_finding` after each version; `replay(max_events=N)` stops without closing the open case. A version calls `pi.at(as_of)`, then `pi.status`, `pi.seen_before` and `pi.memory_refs(factors, case_id)` (fills `repeat` and `refs.pi_memories`); without a PI that has these (the F1 / F2 default) nothing changes. `PiLive` reads through PI's retrieval calls with a **strict** reader (`PiReader(strict=True)`: only what was written strictly before the version's time, because an entry is stamped with its own version's `as_of` and an inclusive read made a rerun read something the first run did not), and logs every read. `earlier_conclusions(record, reader, state_words)` rebuilds the view's p items from the exact PI versions the record names (`PiStore.long_version`); `build_views(..., pi_items=...)` takes them. A PI status never changes a wording class, mode or group (property test).

Regression result (all as tests in `tests/test_loop_real.py`, run in a temp dir, F1 / P1 outputs only read): 284 versions in 116 cases, 51 weekly jobs; every version equals F1 except `repeat` and `refs.pi_memories` (153 `pi_status` and 160 `seen_before` entries changed, `refs.pi_memories` filled in all 284); 85 versions precede the first long-term memory (2025-12-21): structure identical, `pi_status` null, `seen_before` changed in 3 (an entry of another case in the open week, Findings spec 13); PI's five tables are byte-identical to a P1 code-only replay, final statuses identical (25 supported, 3 candidate, 1 retracted); the three as-of audits are clean (the PI-read audit in `loop_engine/audit.py` reads PI's database with its own SQL); two runs identical, a stopped run continues to the same result, a finished run writes nothing; the F1 / F2 / P1 / upstream databases are unchanged (checksums). 106 of 284 views now hold `earlier_conclusions` (so 106 Findings texts need rewriting in L2; the other 178 views and their F2 texts are unchanged); about 85 PI situations-line calls would be needed (estimate). The ambiguities found are in the report and in Findings spec amendment Y / PI spec amendment 46.
